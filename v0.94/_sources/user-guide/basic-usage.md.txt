When you run a simulation in PassengerSim, you will get a
[`SimulationTables`](passengersim.summaries.SimulationTables) object. This object contains a variety
of summary information from the run.

```{code-cell} ipython3
import passengersim as pax

pax.versions()
```

```{code-cell} ipython3
cfg = pax.Config.from_yaml(pax.demo_network("3MKT/08-untrunc-em"))
cfg.simulation_controls.num_samples = 300
cfg.simulation_controls.num_trials = 2
sim = pax.Simulation(cfg)
summary = sim.run()
```

The simple `repr` of this object has a bit of information about what data is in there. You can view
this in a Jupyter notebook by putting the object as the last line of a cell (or just by itself):

```{code-cell} ipython3
summary
```

We can see here there are a variety of tables stored as pandas DataFrames. We can access the raw
values of any of these dataframes directly in Python as an attribute on the
[`SimulationTables`](passengersim.summaries.SimulationTables) object.

```{code-cell} ipython3
summary.carriers
```

## Table reference

Each page below describes the tables available as attributes of `SimulationTables`, including
related derived tables. The documentation on each page describes the public schema of each
DataFrame, not the native counters on the simulation engine or raw SQLite output tables. Callback
outputs are user-defined and live in `summary.callback_data`; they do not have a fixed schema.

Index fields are listed separately from columns. Use `table.reset_index()` to turn index levels into
ordinary columns. Types describe the logical values; pandas dtypes can vary with empty data, missing
values, aggregation, or restored files. Monetary values use the simulation's currency; distances are
in miles. A DCP is a data collection point measured in days before departure.

Unless a page says otherwise, `gt_` fields are totals over non-burned samples. Divide them by
`summary.n_total_samples` for per-sample averages. Ratios with zero denominators can be undefined
(`NaN` or infinity); an absent/disabled collector can return `None`, and an unavailable table can
raise `MissingDataError` rather than return an empty DataFrame. Older archives may contain fewer
fields than the current schemas.

### Selecting extracted tables

Native tables are normally extracted automatically, without entries in `outputs.reports`. Optional
collectors have their own switches, documented on the corresponding page. To restrict which native
tables are extracted, pass a summary instance with a **nonempty** selection:

```python
summary = sim.run(summarizer=pax.SimulationTables(items=["carriers", "legs"]))
```

An empty `items` collection means all native tables, not none. This selection omits tables from
extraction; it does not turn off their engine counters, disable requested database reports, or
prevent derived properties from being computed later. For memory savings, use a table's dedicated
collection switch when one exists. Derived tables need their documented source tables.

(summary-database-backed)=

### Database-backed tables

Database reports require both recording the source data during the run and querying it afterward.
Their pages show minimal `db.write_items` and `outputs.reports` examples. Those lists replace the
configured values rather than adding to them. The default `db.write_items` is `leg_final`,
`fare_final`, `demand_final`, and `bookings`, so include any of these you still need, along with
anything else you record. `outputs.reports` defaults to an empty set; explicitly requesting reports
materializes them while the database is available, which is especially useful for multiprocessing
and `summary_only` storage. `reports: ["*"]` requests all database reports and can be expensive; it
does not enable missing source recording. The wildcard only works as the sole entry:
`reports: ["*", "forecast_accuracy"]` does not request the other database reports.

Removing a report from `outputs.reports` skips eager querying, but accessing its attribute can still
query a retained database. Removing its recording flags stops new source rows; it does not erase
already collected or saved data. Setting `db: null` disables all database recording while leaving
native summaries available. `outputs.html` options control presentation, not collection.

An archived report can be loaded lazily from a PXSIM file. An unmaterialized database report needs
its separate retained database: loading a summary archive does not automatically reopen that
connection. See [summary archives and caches](summary-archives-and-caches) and
[database storage](database/storage.md) for retention and reconnection.

## Metadata

There is also some metadata stored on the summary, which can be accessed via the
[`metadata`](passengersim.summaries.SimulationTables.metadata) method.

```{code-cell} ipython3
summary.metadata()
```

You can access the metadata for a specific key by passing that key as an argument to the method.

```{code-cell} ipython3
summary.metadata("time")
```

## Saving and Restoring

Running a PassengerSim simulation on a practical network can take some time, so it is desirable to
save your results after a run. This allows you to come back to the analyze those results later, or
compare against other future scenario permutations. Results can be saved using the
[`SummaryTables.to_file`](passengersim.summaries.SimulationTables.to_file) method.

```{code-cell} ipython3
---
tags: [hidden]
---
# ensure the saved-outputs directory starts off empty
import shutil

shutil.rmtree("saved-outputs", ignore_errors=True)
```

```{code-cell} ipython3
summary.to_file("saved-outputs/summary")
```

The method will automatically add the appropriate file extension and write the file to disk. By
default, it will also add a timestamp, so that you will not overwrite existing similar files.

```{code-cell} ipython3
from passengersim.utils.show_dir import display_directory_contents

display_directory_contents("saved-outputs")
```

Restoring from this file can be done, surprisingly enough, using the
[`SimulationTables.from_file`](passengersim.summaries.SimulationTables.from_file) classmethod. You
can call this function with the same filename as `to_file`, and it will load the file with the most
recent timestamp if there is one or more matching file(s) with various timestamps. To load a
specific file that may or may not be the most recent, you can call this method with the complete
actual filename, including the timestamp and ".pxsim" suffix.

```{code-cell} ipython3
resummary = pax.SimulationTables.from_file("saved-outputs/summary")
resummary
```

When opening the file, only the most basic metadata is actually loaded by the
[`from_file`](passengersim.summaries.SimulationTables.from_file) method, and the rest is identified
as available on demand from storage. You can confirm which file is used as the storage, as that is
added to the metadata at load time:

```{code-cell} ipython3
resummary.metadata("store")
```

Accessing data will load just that table from the file. This includes accessing a table explicitly
(by calling for it), or implicitly (e.g. by creating a figure using the data). The loading process
happens transparently -- you don't need to specifically load anything, it will just happen
automatically as needed.

```{code-cell} ipython3
resummary.carriers
```

```{code-cell} ipython3
resummary.fig_fare_class_mix()
```

We can see in the objects `repr` that the carriers and fare_class_mix tables have been loaded, but
the rest are still only in the storage file.

```{code-cell} ipython3
resummary
```

In addition to the summary data tables, the complete configuration used is also still available, in
case it is needed.

```{code-cell} ipython3
resummary.config
```

## Pickling

In addition to the `pxsim` file format, PassengerSim also supports `pickle` serialization. This file
format loses some of the niceties of the `pxsim` format, such as lazy data loading. But it is a
widely adopted standard format for Python serialization which is used across many Python libraries.
If the LZ4 library is available, it will also use that for compression, which can result in a
marginally smaller filesize than the `pxsim` format.

```{code-cell} ipython3
summary.to_pickle("saved-outputs/summary")

display_directory_contents("saved-outputs")
```

Restoring from this pickle file can be done, surprisingly enough, using the `from_pickle` method.
You can call this method with the same filename as `to_pickle`, and it will load the file with the
most recent timestamp if there is one or more matching file(s) with various timestamps. To load a
specific pickle file that may or may not be the most recent, you can call this method with the
complete actual filename, including the timestamp and ".pkl" or ".pkl.lz4" suffix.

```{code-cell} ipython3
resummary2 = pax.SimulationTables.from_pickle("saved-outputs/summary")
resummary2
```

You may note the summary that is reloaded from the pickle file is fully populated, with every table
showing as a DataFrame instead of "available from store". Since the pickle format does not include
lazy data access, loading anything from a pickle requires loading everything from the pickle, which
may take some time for larger simulations.

### Large PXSIM outputs and compatibility

New PXSIM exports use chunked storage, allowing a result to exceed SQLite's single-value size limit.
Existing PXSIM files remain readable without conversion. Saving a new copy uses the new format,
which requires a current reader; older PassengerSim releases cannot read it.

Loading remains lazy by summary table, but accessing a table still needs enough memory for the
complete restored object. For schema, compression, validation, and compatibility details, see
[PXSIM storage format](../mechanics/pxsim-storage.md).

To protect an archive from explicit data removal, open it read-only:

```python
summary = pax.SimulationTables.from_file("results.pxsim", read_only=True)
```

Loading an archive restores its summaries, configuration, and metadata. Detailed simulation data
stays in a separate SQLite file and is not opened automatically. Close the result, or use a context
manager, to release the archive handle. See
[summary archives and caches](summary-archives-and-caches) for keeping or deleting detailed data
independently of saved summaries.

Only load trusted PXSIM files: they contain Python pickle payloads. Integrity checks detect
corruption but do not authenticate the source.

## Simulation size defaults and migration

New configurations that omit simulation counts now use **3 trials**, **350 samples per trial**, and
**50 burn samples per trial**. That means 1,050 simulated samples and 900 usable samples across the
trials. Previously, the defaults were 1 trial, 600 samples, and 100 burn samples, producing 500
usable samples. This changes runtime, resource use, and statistical results for scripts that rely on
defaults. It is a simulation configuration change, independent of the PXSIM storage format.

Explicit counts in existing configurations, including configurations restored from PXSIM files,
remain unchanged. To retain the earlier run size, specify:

```yaml
simulation_controls:
  num_trials: 1
  num_samples: 600
  burn_samples: 100
```

PassengerSim recommends at least 50 burn samples per trial and 750 usable samples across trials; the
earlier defaults therefore produce a usable-sample warning. See
[Counting Simulations](../mechanics/counting-sims.md) for the distinction between trials, samples,
and burn periods.
